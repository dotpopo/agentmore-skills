# 解释视频

适合抽象概念、随时间展开的机制、需要"看着它变化"才能懂的内容。风格借鉴 3Blue1Brown：先建立直觉，再引入符号；一个画面讲一个想法；画面的连续变化本身就是论证。不冒充原作者，不复制其品牌标识，不模仿其本人声音。

## 先确认你能做什么

动手之前检查环境里实际有什么，不要假设。

- **画面**：常用 Manim。没有就用环境里能逐帧生成动画的方式，例如脚本画 SVG/Canvas 帧再合成。
- **配音**：优先用内置配音。需要本地方案时，用实际可用且获授权的本地 TTS。只有用户明确要求某个外部声音服务（如 ElevenLabs）时才考虑对应集成，并且不在对话里索要明文密钥。
- **字幕**：默认提供。不能嵌入时，交付字幕文件或逐字稿。
- **合成**：ffmpeg 或等价工具。

关键工具缺失时，直接说缺什么，退一步交付"脚本 + 分镜 + 可运行的渲染代码"或带字幕的短片段。分镜和脚本是中间产物，不是最终视频，不要把它们说成视频。

## 参数

| 项目 | 默认 |
|---|---|
| 时长 | 简单主题 60–90 秒，复杂主题 2–3 分钟，按实际能力调整 |
| 画幅 | 16:9。明确面向手机短视频时用 9:16 |
| 语言 | 与用户一致 |
| 结构 | 核心问题 → 建立直觉 → 动态机制 → 关键结论 → 适用边界 |

## 制作流程

1. **先写讲稿，不要先写代码。** 旁白用 STE 风格，短句，一句一个想法。
2. **拆分镜。** 每个镜头对应一两句旁白，写明画面里出现什么、怎么变化。
3. **画面服务于旁白。** 旁白说"两个量一起增长"，画面里就要有两个量一起增长。讲到哪个对象就突出哪个对象，不用无关素材填充。
4. **渲染并检查。** 抽查一两帧：文字有没有溢出、重叠，对比度够不够。
5. **交付。** 视频文件加一段文字摘要（核心结论、关键参数、适用边界），方便回查。

## 画面原则

- 一个画面只讲一个想法，信息逐步出现，不一次摆满。
- 同一个对象全程保持同样的名称、颜色和符号。
- 文字要少，能用图形表达的不用文字。
- 变化要有目的，移动、变形、高亮都应该在说明某个关系。
- 关键变换和公式出现后，留出理解的时间。
- 深色背景、高对比、字号足够大。
- 数学和数据要精确，用可控渲染与合成，不要把公式的正确性寄托在生成式画面上。

## 什么时候不要做视频

- 一张图加几句话就能讲清楚。
- 用户只是随口问问，没有表现出愿意花几分钟看的意思。
- 内容是精确的参考信息（命令、参数表），视频反而难检索。

这些情况先给文字和图，再用一句话提议可以做成视频。
